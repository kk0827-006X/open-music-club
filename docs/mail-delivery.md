# 访问申请与最终投递确认

> 2026-10-27：本文下方记录的是上一版投递阻塞流程。当前申请以邮箱验证后进入后台为准，管理员提醒不再阻塞审批，旧初始密码流程已替换；现行配置、接口与恢复规则见 [申请审核与自动激活](application-activation.md)。历史投递记录及阿里云最小权限说明保留。

## 判定与恢复

申请记录和通知关联先在 SQLite 事务内落库，再发送 SMTP。SMTP 接受仅返回 202（等待），**阿里云最终投递成功**才返回 201 / `success:true`。明确 SMTP 拒绝或阿里云明确失败返回 502，原邮箱可复用原申请重试。超时、断线、查询失败只能标为未知，不自动重发、不谎报成功。

每条申请仅增加一条通知记录，重试覆盖旧尝试。唯一随机主题、发件与收件地址精确匹配阿里云记录；保存 Message-ID 便于关联，但查询接口并不返回 Message-ID，不能拿它伪造匹配。每次最多读取三页、每页 100 条，未读完不能确认成功。查询有总超时、数据库 10 秒冷却及 lease，过期结果不能覆盖新尝试。

匿名申请者只能在原 Session 查询 `/api/applications/:id/notification`；同 Session 重提未决或已送达申请恢复回执，不重复发信。丢失 Session 后不能凭编号或邮箱查询未决申请，应联系管理员核实。弹窗最多自动查询六次，之后可手动查询；关闭即停止。管理员审批时也查询最终状态，防止申请人关闭页面后流程卡死。历史没有通知记录的申请仍可按原规则审批。

申请通知未送达不能批准；拒绝和已完成审批的结果不会因发送审核结果通知失败而回滚。不通过邮件发送密码、TOTP、恢复码或申请理由。

## 本机配置

1. 阿里云 RAM 新建专用用户/角色，最小权限自定义策略如下。不要使用主账号密钥，不授予发信、删除或完整邮件管理权限。

```json
{"Version":"1","Statement":[{"Effect":"Allow","Action":["dm:SenderStatisticsDetailByParam"],"Resource":["*"]}]}
```

2. 只在本机受保护的 `.env` 填写 `.env.example` 中的 `ALIYUN_DM_ACCESS_KEY_ID`、`ALIYUN_DM_ACCESS_KEY_SECRET`；STS 还须填写 `ALIYUN_DM_SECURITY_TOKEN` 并由运维更新过期凭据。区域为 `cn-hangzhou`，API 固定 HTTPS `dm.aliyuncs.com`。这些凭据不同于现有 SMTP 密码，绝不发送到前端。
3. 保留现有 `MAIL_ENABLED=true`、SMTP TLS 设置。`MAIL_FROM` 是网站发件地址；`MAIL_ADMIN_TO` 是真正可收信的管理员邮箱，留空则使用 `ADMIN_EMAIL`。`noreply` 发信地址不等于一个可登录的收件箱。
4. 重启后端后发起一次实际申请。在弹窗观察“等待确认→申请成功”，并到阿里云投递详情及管理员邮箱核对。未配置凭据时返回 503，不会创建新申请或发送通知。

“投递成功”代表收件服务器接受，不保证进入收件箱分类、未被放入垃圾箱，更不代表管理员已阅读。官方状态依据：[SenderStatisticsDetailByParam](https://help.aliyun.com/zh/direct-mail/api-dm-2015-11-23-senderstatisticsdetailbyparam)。查询留存窗口外和上游不可用的结果继续未知，不能据此自动重发。

## 验收边界

单元、数据库/HTTP 和浏览器测试均使用临时数据库、模拟 SMTP 与模拟投递记录，不发送真实邮件。真实 RAM 权限、查询时间窗口、阿里云记录延迟及 Gmail 实际送达必须在填写凭据后单独验收；不能把 Mock 通过等同于实发验证。依赖锁定官方 `@alicloud/dm20151123`，旧 Node 类型安装脚本明确禁用；未新增常驻后台轮询、公开回调或消息队列。
